# AI upgrade — decisions (one line each)

- 2026-10-03: The brief says the app header reads "Magical Party (do not rename)"; the owner explicitly asked earlier the same day to rename the wordmark to "Magical Birthday Planner", which shipped in a50a5fb before this branch. The AI work does not rename anything further.
- 2026-10-03: The OpenCode key provided in chat is stored only in the operator's local secrets file (~/.config/mbp-secrets/env, chmod 600) as OPENCODE_API_KEY. It is not in the repo, not in Vercel; the human sets AI_API_KEY in Vercel (LAUNCH_CHECKLIST). Rotate it after launch (it was pasted into chat).
- Provider: AI_PROVIDER=opencode → generic OpenAI-compatible adapter; base URL https://opencode.ai/zen/go/v1, model deepseek-v4-pro, Bearer auth + required `x-opencode-session` header (verified against official docs + one live call). JSON mode used (`response_format: json_object`); reasoning_content is discarded.
- No new dependencies: the adapter uses fetch (no SDK) so timeouts/abort/headers are explicit; zod 3.23.8 already present.
- Entitlements: code has NO per-plan gating today; marketing promises a matrix. lib/ai/capabilities.ts follows the brief's table adjusted to marketing: budget_optimizer + food = Pro only (pricing: "Smart budget tracker", "food suggestions" are Pro); activities = Plus+ ("Personalized activity ideas"); checklist/invitation/timeline = Starter+ (Starter: "Smart checklist & timeline", "invitation creator"); theme_ideas + party_planner = limited on Free.
- Trial: a 24 h sign-up trial resolves to plan PRO in getUserPlan; for AI it counts as the Free tier (source === 'trial' → FREE limits) so a trial can't burn Pro-tier generations. Super Admin overrides apply as their plan (plan switching keeps working) and Super Admin bypasses AI limits.
- Plan lookup reuses the existing trusted resolver getUserPlan (service role, read/recompute only). AI code never writes user data with the service role; all AI writes use the user's RLS session or narrow security-definer RPCs scoped to auth.uid().
- ai_generations: users get SELECT on their own rows only (no direct INSERT/UPDATE). Reserve/finalize/mark-applied go through security-definer RPCs restricted to the caller's own party and pending rows — direct UPDATE would let a user flip used generations to failed and reset their limits.
- Limits are race-safe without locks: reserve a pending row, then rank it among the party's/user's counted rows (pending|success, ordered by created_at,id); over-cap rows are finalized as `rejected` and don't count.
- Failed generations (provider/timeout/invalid) don't count toward per-party caps; pending + success do. Global daily breaker counts all non-rejected rows via a security-definer aggregate (returns a number only).
- New tables (no existing target): party_ai_activities (party_activities requires a catalogue activity_id), party_shopping_items, party_budget_lines — all RLS via owns_party(), same pattern as checklist_items.
- Food results apply to the shopping list (and optionally checklist); invitation results prefill the existing editor (no new table, never sent automatically); timeline is view/copy + "Add to checklist" for prep items.
- The existing /api/themes/ai (Azure) route and its UI stay untouched for backward compatibility; theme_ideas is the new, gated path.
- Migrations are applied only to the local Supabase stack; production is the only remote DB, so nothing is applied there (LAUNCH_CHECKLIST lists them).
